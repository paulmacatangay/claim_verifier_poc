Chapter 1 The Relational Model
1.1 Relations and Keys
A relation is a table made of rows and columns. Each row is called a tuple and each column is called an attribute. A relation schema lists the attributes of a relation together with the domain of each attribute. A superkey is a set of attributes that uniquely identifies each tuple in a relation. A candidate key is a minimal superkey, which means that no proper subset of it is still a superkey. The database designer chooses one candidate key to be the primary key of the relation. The primary key values of different tuples must be distinct, and no attribute of the primary key may be null. A relation can have several candidate keys but it has only one primary key. Choosing a primary key whose values rarely change helps keep references to the relation stable over time.1.2 Foreign Keys and Integrity
A foreign key is a set of attributes in one relation that refers to the primary key of another relation. The relation that contains the foreign key is called the referencing relation, and the relation that it points to is called the referenced relation. Referential integrity requires that every non-null foreign key value appears as a primary key value in the referenced relation. If a delete or an update would break this rule, the database system can reject the operation or it can propagate the change to the referencing tuples. Entity integrity requires that no primary key attribute is null. Together these two constraints keep the data in a relational database consistent without relying on application code to check every change. A foreign key may be null when the relationship it records is optional.Chapter 2 Normalization
2.1 Functional Dependencies
A functional dependency states that the values of one set of attributes determine the values of another set of attributes. We write A determines B when two tuples that agree on A must also agree on B. A functional dependency is a constraint on the schema and it must hold for every legal instance of the relation. Every key determines all the other attributes of its relation. A dependency is trivial when the right side is a subset of the left side. Designers use functional dependencies to find redundancy, because a dependency whose left side is not a key means that the same fact can be stored many times. The axioms of reflexivity, augmentation and transitivity allow all the dependencies that follow from a given set to be derived.2.2 Normal Forms
A relation is in first normal form when the domains of all its attributes are atomic. A relation is in Boyce-Codd normal form when, for every nontrivial functional dependency A determines B, the set A is a superkey. Third normal form is slightly weaker, because it also allows a dependency whose right side attributes belong to some candidate key. Every Boyce-Codd normal form relation is also in third normal form, but the reverse is not true. Decomposing a relation to reach a higher normal form removes redundancy, but a good decomposition must be lossless, which means that joining the parts gives back exactly the original relation. It is not always possible to obtain a dependency preserving decomposition into Boyce-Codd normal form, while a dependency preserving decomposition into third normal form always exists.Chapter 3 Transactions
3.1 ACID Properties
A transaction is a unit of work that accesses and possibly updates data items. The ACID properties describe what a database system guarantees for transactions. Atomicity means that either all the operations of a transaction take effect or none of them does. Consistency means that a transaction run alone on a consistent database leaves the database consistent. Isolation means that concurrent transactions behave as if they ran one after another. Durability means that once a transaction has committed, its changes survive system failures. The recovery system uses a log to restore atomicity and durability after a crash, while the concurrency control system is responsible for isolation. Each property is provided by a different component of the database system, and the properties are not independent of one another.3.2 Concurrency Control
A schedule is serializable when its effect is the same as the effect of some serial schedule. Two-phase locking is a protocol that guarantees serializability. In the growing phase a transaction may obtain locks but may not release any, and in the shrinking phase it may release locks but may not obtain any. A shared lock allows a transaction to read a data item, and an exclusive lock allows it to read and write the item. Several transactions can hold a shared lock on the same item at the same time, while an exclusive lock can be held by only one transaction. Locking can cause deadlock, in which two or more transactions wait for each other forever. The system resolves a deadlock by rolling back one of the transactions.
